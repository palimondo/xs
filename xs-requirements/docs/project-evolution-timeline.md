# xs Project Evolution Timeline

xs (explore-session) is a CLI tool for working with Claude Code session transcripts. It started as a side project inside BookMinder, outgrew its host, and is now being recreated as a standalone tool with proper test discipline. This document captures how we got here and why.

---

BookMinder was a Python CLI tool for extracting highlights from Apple Books, started in May 2025. Development used Claude Code with strict TDD. A side practice emerged early: copying full session console output into day log files and feeding them to Gemini for high-level summaries. This was just journaling at first — a way to keep track of multi-day work. It became important later.

The problem that created xs had several parts. Terminal sessions were fragile — a Warp update could close a session and lose the scrollback. Day logs got truncated when terminal buffers overflowed. When BookMinder added GitHub Actions CI with Claude Code Action, the ability to create GitHub issues and let Claude Code prepare or review PRs was genuinely useful — it meant project work could continue without being at the computer. But a GitHub Action bug where the branch with changes was not pushed at the end of a session meant work got completely lost. Session transcripts embedded in workflow logs disappeared with the ephemeral runner. The core issue across all of these was the same: valuable work context was disappearing.

The first solution was a JQ script called reconstruct.jq, built in July 2025 to recover a truncated day log from the raw JSONL that Claude Code stores in ~/.claude/projects/. Development was driven by character-level comparison against actual Claude Code console output. The formatting had to match exactly. This console fidelity requirement carried forward into everything that followed.

The motivation for recovering and preserving these transcripts goes beyond convenience. The process for creating an artifact is as important as — if not more important than — the final product, if we want reliable software built through a reliable process. The process must be repeatable, understandable, and continuously improvable, which is impossible without systematic analysis. Since LLMs are pure functions with built-in stochastic variation, the function and reliability of the system can only be understood using statistical methods. Preserving all inputs — including full session transcripts — is essential for that analysis.

JQ couldn't scale to filtering, search, or multiple display modes, so the tool was rewritten in Python as explore_session.py later that July. Over a few intense sessions it gained fuzzy session lookup, a filter syntax borrowed from Claude Code's own allowedTools format, search with grep-style context lines, range selection, and three display modes (compact, truncated, full). A summary mode was designed as a self-documenting entry point where each statistic shows the CLI flag needed to drill deeper. The design was shaped heavily by user corrections — rejecting decorative formatting, enforcing separation between filtering and display, insisting on stable sequence numbers that don't change when filters are applied.

A fourth use case emerged unplanned: compaction recovery. When Claude Code compacts context (automatically or via /compact), it summarizes away details that are often critical — exact file paths, error messages, design rationale, prior corrections. The failure mode was specific and recurring: after compaction, the agent would pick up a task and run with it, ignoring decisions made earlier in the same session. xs already had the capabilities needed to recover this lost context (search, range selection, full content display), so a hook-based architecture was built on top: detect compaction, block the next tool call, inject recovery instructions that use xs to retrieve what was lost. This use case is central to the reimplementation — xs is infrastructure for the agent's own continuity.

By late July 2025, explore_session.py had reached 1,625 lines — larger than BookMinder itself. It worked and solved real problems, but it was built through rapid interactive development without the TDD discipline BookMinder had. Characterization specs were added after the fact, matching the implementation rather than specifying desired behavior. When Claude Code's JSONL format changed between versions 1.x and 2.x, the implementation ended up in an inconsistent state — some parts updated, others not — and the specs couldn't distinguish intentional behavior from bugs. Trust in the codebase was low.

The decision to recreate xs from scratch came from recognizing that the tool's real requirements were embedded in session transcripts and user corrections, not in the code or its tests. The approach: recover requirements from the original development sessions first, validate them, then reimplement with strict TDD. In January 2026, a requirements recovery process mined day logs and session transcripts in multiple passes — cataloging sessions, extracting findings through subagent-based sequential reading, cross-referencing across sources, and synthesizing into stories with acceptance criteria. An initial keyword-search approach was abandoned after recognizing it as confirmation bias — pre-formed hypotheses just got confirmed by their own search terms. The alternative was chronological reading, letting requirements emerge through the material rather than searching for expected patterns. The recovery produced 108 stories across 12 epics and nine design principles. These recovered requirements, grounded in the actual development record, are the basis for the TDD reimplementation.

The core problem xs addresses — losing the thread — shows up at every level. Terminal sessions disappear. Context gets compacted away. Agents forget corrections made minutes earlier. LLMs have no continual learning, so every session starts from zero unless the context is explicitly provided. xs exists because session transcripts are the only durable record of what actually happened, and without a tool to make them accessible, that record is useless. The recreation project exists because the first implementation accumulated its own form of the same problem: working software that nobody fully understands, built through a process that wasn't recorded in a trustworthy way. The transcripts that documented the original development are now the authoritative source for doing it properly.

## Future Directions

Beyond the immediate TDD reimplementation, xs should evolve toward systematic analysis of session transcripts using methods from design cognition research. Cognitive scientists have decades of established methodology for studying how designers solve problems — protocol analysis, the FBS (Function-Behavior-Structure) coding scheme, Linkography — all developed through empirical studies of designers working on ill-structured problems. Session transcripts are structurally similar to think-aloud protocols used in these studies: a timestamped record of problem-solving behavior including decisions, corrections, and dead ends. Applying these analytical frameworks to agentic AI sessions could make it possible to study how AI-assisted development actually works as a cognitive process — not just whether the output is correct, but how the problem-solution co-evolution unfolds, where constraint construction happens, and what failure modes emerge. This connects to the broader research threads around Distributed Cognition (Hutchins) and Activity Theory (Engeström), where tools are understood not as passive aids but as components that transform the cognitive system itself.

On the tooling side, xs currently supports Claude Code session transcripts only. As AI-assisted development diversifies across platforms — Codex CLI and others — xs should expand to support additional transcript formats, making cross-platform analysis possible.
